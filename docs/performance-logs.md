# 本地性能记录

包含此功能的新版App启动后自动记录，不需要打开调试器。日志仍在「设置 → 日志」，保留最近24小时、最多128 MiB，不上传。源码或网页预览更新不代表已安装App更新；需要更新安装包后，才能采集该版本的真实卡顿。

## 怎么区分后台慢与界面卡顿

事件为`performance`的记录每10秒汇总，不逐帧写磁盘。`api`、`git-read`及`provider-read`保留逐请求时间；前端请求用`requestId`关联，Git用`spanId`和匿名`resource`关联开始/结束。

| 阶段 | 主要字段 | 含义 |
| --- | --- | --- |
| `ui-window` | `frameMaxMs`、`slowFrames`、`lagMaxMs` | 交互期间rAF回调间隔超过50ms的次数、最大间隔；1秒心跳的额外调度延迟。不是屏幕实测FPS，也不单独证明磁盘或CPU原因。 |
| `ui-window` | `inputMaxMs`、`nextFrameMaxMs` | 输入事件创建到处理、处理到下一次rAF机会的最大等待。下一次rAF不等于像素已显示。 |
| `ui-window` | `longTaskSupported`、`longTasks`、`longTaskMaxMs` | 支持Long Tasks接口时才采集；supported为0表示该项不可用，不表示没有卡顿。rAF和心跳仍记录。 |
| `dashboard-render` / `branch-render` | `renders`、`renderMaxMs`、`renderTotalMs`、`items` | 组件函数进入到layout effect提交的观测耗时，包含子树提交影响；分别表示仓库数或分支数。不是纯CPU、布局或绘制耗时。 |
| `ui-window` | `activeRequests`、`peakRequests` | 本窗口结束时正在等待的业务请求与窗口峰值，不含日志传输；等待本身不是GUI卡顿证据。 |
| `response-read` / `response-validate` | `durationMs`、`bytes`、`tasks` | 浏览器响应体接收与解码合计，以及已取得结果的同步校验耗时。bytes仅在Content-Length可用时记录，不额外序列化/编码大响应；原生IPC解码不可拆分。 |
| `git-read` / `git-write` | `queueMs`、`durationMs`、`bytes`、`activeRequests` | 等待读取/fetch许可的时间、整次命令耗时、输出字节数和该队列正在运行的命令数；不记录输出文本。duration包含排队，不能直接称为纯磁盘耗时。 |
| `log-write` | `writeMs`、`queueMs`、`queued`、`dropped` | 后台日志写入累计耗时、排队最大等待及积压/丢失；只按窗口汇总，不递归记录每次日志写入。 |
| `renderer-log-queue` / `log-queue` | `dropped` | 前端传输与后台写入各自丢失的数量。设置会显示记录可能不完整；不要把丢失的记录当作没有发生问题。 |

后台请求耗时很长，而帧/输入/渲染指标仍低，说明该段等待没有表现为已观测的主线程卡顿。它并不能证明其他时段、系统合成/GPU或已安装版本都正常。请求并行数和卡顿同时变大只说明相关，需要结合渲染、校验及Git排队/执行的时间继续确认，不能单凭相关性认定网络、磁盘或Codex为根因。

## 记录自身的开销和边界

- 前端最多积压128条、一次只发送1条；后台最多积压512条，单独线程一次最多批量写64条。磁盘变慢时不让日志文件操作占用GUI或异步服务工作线程；超限或写失败会计数并反馈，不无限占内存。
- 后台Git只读命令最多4个并行，fetch最多2个；其余异步等候许可并支持取消。实际写命令不占这两种后台许可，但它所需的只读检查仍可能排队；加载状态直到真实结束才清除。没有删减索引、分支、目录或提交信息。
- 打开/复制日志前有写入屏障，清理/列举/复制在阻塞工作线程执行。日志维护每分钟进行；正常异步记录表示已入队，不承诺已经落盘。进程被强杀时最后尚未写入的队列可能丢失。
- 大于40个分支的展开不做逐行高度动画，也不为启动动画强制测量表格布局；用分支索引避免逐行扫描全列表。完整分支仍会挂载，超大列表的首次渲染可能昂贵，不能把这一轮轻量修正当作完整虚拟化或“所有卡顿已解决”。
- 不记录按键文本、按钮文字、文件内容、原始响应、账号名称、地址、令牌或本地路径。不采集操作系统磁盘吞吐/其他应用文件活动，因此不能直接证明外部Codex正在争抢磁盘。

本轮受控验证使用合成600分支与临时Git/日志目录，未用用户凭据，未操作正在运行的安装版。真实卡顿的日志与根因分析需要在更新后的App中复现后单独确认。
